# 服务端开发计划 —— 语音翻译网关

> 配套文档：[功能 5 音频开发计划](feature5_audio_plan.md)（设备端）
> 状态：⏸ 待评审 · 硬件未就绪，先做服务端

## 1. 可行性结论

**可行。** 这类「按下说话 → 识别 → 翻译 → 合成朗读」的设备已有成熟产品（翻译机、AI 翻译耳机），
技术上没有无法逾越的障碍。逐环节看：

| 环节 | 成熟度 | 说明 |
| ---- | ---- | ---- |
| 设备录音 + WebSocket 上传 | ✅ 高 | ESP32 常规能力，需注意 WiFi 稳定性 |
| 语音识别 ASR | ✅ 高 | 云服务商都有现成 API，中文准确率好 |
| 翻译 | ✅ 高 | 用对话模型 + prompt 即可，质量足够日常对话 |
| 语音合成 TTS | ✅ 高 | 音色可选、支持流式返回 PCM |
| 端到端时延 | ⚠️ 需优化 | 朴素实现 4~6 秒，优化后 2.5~3.5 秒 |

需要提前纠正一个概念：**DeepSeek 没有专门的「翻译模型」**，只有 `deepseek-chat` / `deepseek-reasoner`
这类通用对话模型，翻译通过 prompt 完成。好处是它兼容 OpenAI 接口、价格低、中文语感好；
代价是需要**约束输出格式**（模型有时会附加解释、或把原文回显），要靠 prompt + 结果校验兜住。

## 2. 关键技术决策（有推荐值，可改）

### 2.1 音频格式约定 —— 这是整个系统的地基

设备端 ES8388 的 ADC 和 DAC **共用 LRCK**（寄存器 `DACCONTROL21=0x80`），
所以录音和播放**必须同采样率**，不能一边 16k 一边 24k。据此定契约：

| 方向 | 格式 | 理由 |
| ---- | ---- | ---- |
| 设备 → 服务端 | **PCM s16le，24kHz，单声道，20ms/帧（960 字节）** | 设备零处理，直接送 I2S 采样 |
| 服务端 → 设备 | **PCM s16le，24kHz，单声道** | **设备无需任何解码器**，直接灌 I2S |

不选 Opus/MP3 的原因：设备端解码要占 CPU 和代码空间，而 48KB/s 的 PCM 在 WiFi 下完全够用
（3 秒语音 = 144KB）。带宽真成问题时再加 Opus，协议留好 `format` 字段即可。

**服务端负责所有格式转换**：24k → ASR 需要的 16k（重采样）、PCM → WAV 封装（加 44 字节头）。
设备端全程不做格式转换，这是让 C 代码保持简单的关键。

### 2.2 交互模式：批量而非流式（第一版）

| 模式 | 延迟 | 复杂度 | 结论 |
| ---- | ---- | ---- | ---- |
| 批量：说完 → 整段上传 → 返回 | 较高 | 低 | ✅ **第一版用这个** |
| 流式 ASR：边说边传，返回中间结果 | 低 | 高 | 阶段 6 再考虑 |

按住说话本身就是「有明确起止」的交互，批量识别完全够用，且 ASR 送整段音频的准确率反而更高
（有上下文）。协议里预留 `asr` 消息的 `final` 字段，将来加流式不用改协议。

### 2.3 服务端技术栈

| 组件 | 选择 | 理由 |
| ---- | ---- | ---- |
| 语言 | Python 3.11+（本机 3.13.16） | AI 生态最全，接三方 API 最快 |
| Web 框架 | **FastAPI + uvicorn** | 原生支持 WebSocket，异步并发好 |
| HTTP 客户端 | **httpx**（async） | 统一异步，避免阻塞事件循环 |
| 重采样 | **soxr**（回退 scipy） | 质量高、速度快；scipy 也可但慢一些 |
| 配置 | pydantic-settings + `.env` | 密钥不入库 |
| 日志 | structlog 或标准 logging + JSON | 便于事后算延迟 |

> 不用 Node/Go 的原因：三条 AI 链路都是 HTTP+JSON，Python 写起来最短；
> 真要追求并发再换，接口抽象好之后换语言成本可控。

### 2.4 服务商抽象

把三家都做成**可插拔适配器**，通过配置切换（便于比价、便于降级）：

```
providers/
  asr/        base.py  aliyun.py  tencent.py  openai_whisper.py  mock.py
  mt/         base.py  deepseek.py  mock.py
  tts/        base.py  aliyun.py  tencent.py  azure.py  mock.py
```

好处：**mock 适配器让整套系统在没有任何 API Key 的情况下就能跑通**（识别返回固定文本、
合成返回正弦波），这对"硬件未就绪"的当前阶段价值极大 —— 可以先验证协议和播放链路。

### 2.5 部署形态

| 阶段 | 形态 | 说明 |
| ---- | ---- | ---- |
| 开发 | 本机 `ws://192.168.x.x:8000` | 设备同一局域网，明文，无鉴权 |
| 上线 | 云服务器 + Nginx + `wss://` | 需 TLS 证书；设备侧要配 CA bundle |

⚠️ ESP32 用 `wss://` 需要证书 bundle，代码空间和握手耗时都会增加。
**建议第一版就用 `ws://` 在局域网跑通**，等设备端稳定后再加 TLS。

## 3. WebSocket 协议设计

设计原则：**为 C 客户端服务** —— 扁平 JSON、单层嵌套、消息短、二进制帧定长。

### 3.1 帧类型

| 类型 | 用途 |
| ---- | ---- |
| 文本帧（JSON） | 控制与文本结果 |
| 二进制帧 | 纯 PCM 音频，无头部，长度由帧边界决定 |

### 3.2 设备 → 服务端

```json
{"t":"hello","ver":1,"dev":"esp32-a1b2","au":{"rate":24000,"ch":1,"bits":16}}
{"t":"utt_start","id":7,"from":"auto","to":"en","voice":"female-1"}
   ← 随后是多个二进制帧，每帧 960 字节（20ms）
{"t":"utt_end","id":7}
{"t":"abort","id":7}
{"t":"ping"}
```

### 3.3 服务端 → 设备

```json
{"t":"hello_ok","ver":1,"sid":"s-3f9a","au":{"rate":24000,"ch":1,"bits":16}}
{"t":"asr","id":7,"text":"你好，今天天气不错","lang":"zh","final":true}
{"t":"mt","id":7,"text":"Hello, the weather is nice today.","from":"zh","to":"en"}
{"t":"tts_begin","id":7,"rate":24000,"ch":1,"bits":16,"bytes":96000}
   ← 随后是多个二进制帧，PCM
{"t":"tts_end","id":7}
{"t":"err","id":7,"code":"asr_empty","msg":"没听清"}
{"t":"pong"}
```

### 3.4 时序（设备端视角）

```
设备                          服务端
 │  utt_start(id=7)             │
 │ ──────────────────────────▶  │
 │  PCM 帧 × N                  │
 │ ──────────────────────────▶  │  缓冲、重采样、封 WAV
 │  utt_end(id=7)               │
 │ ──────────────────────────▶  │
 │                              │  → ASR
 │  ◀────────────────────────── │  asr  (立即上屏，用户先看到自己说了什么)
 │                              │  → 翻译 → TTS
 │  ◀────────────────────────── │  mt   (上屏译文)
 │  ◀────────────────────────── │  tts_begin
 │  ◀────────────────────────── │  PCM 流式下发（边生成边发）
 │  ◀────────────────────────── │  tts_end
```

关键设计：**识别结果先回、音频后到**。用户松开按键后约 1 秒就能看到「识别出的原文」，
主观等待感大幅下降 —— 这比单纯优化总时长更有效。

### 3.5 错误码约定

| code | 含义 | 设备行为 |
| ---- | ---- | ---- |
| `asr_empty` | 没识别出内容（静音/太短） | 显示"没听清，请再说一次" |
| `asr_fail` | ASR 服务异常 | 显示"识别失败" |
| `mt_fail` | 翻译失败 | 仍显示原文，提示翻译失败 |
| `tts_fail` | 合成失败 | 只显示文本，不播放 |
| `busy` | 上一句还没处理完 | 忽略/提示稍后 |
| `bad_proto` | 协议错误 | 重连 |

原则：**任何一环失败都不让整次交互白费** —— 有文本就先显示文本。

## 4. 服务端要做的东西

### 4.1 模块清单

| 模块 | 职责 | 复杂度 |
| ---- | ---- | ---- |
| `gateway/ws.py` | WebSocket 接入、会话生命周期、心跳 | 中 |
| `gateway/session.py` | 单设备状态机（idle→recording→processing→playing） | 中 |
| `gateway/protocol.py` | 消息编解码与校验（pydantic 模型） | 低 |
| `audio/resample.py` | 24k↔16k 重采样、PCM/WAV 互转、静音检测 | 低 |
| `pipeline/orchestrator.py` | 串联 ASR→MT→TTS，控制并发与超时 | **高** |
| `providers/asr/*` | ASR 适配器 + mock | 中 |
| `providers/mt/*` | 翻译适配器 + mock | 低 |
| `providers/tts/*` | TTS 适配器 + mock（支持流式） | 中 |
| `observability/timing.py` | 每阶段耗时埋点、结构化日志 | 低 |
| `config.py` | 配置与密钥（.env） | 低 |
| `tools/sim_client.py` | **桌面模拟设备**（见 4.2） | 中 |

### 4.2 桌面模拟客户端 —— 这是当前阶段最重要的工具

硬件没就绪，但**服务端可以被完整验证**。写一个 Python 客户端扮演设备：

```bash
# 用 wav 文件模拟一次完整交互
python tools/sim_client.py --wav test_zh.wav --from zh --to en

# 输出示例
[asr ] 你好，今天天气不错            (620 ms)
[mt  ] Hello, the weather is nice today.   (840 ms)
[tts ] 收到 92160 字节 PCM / 1.92 s      (首字节 310 ms)
[总  ] 2.41 s   → 已保存 reply.wav
```

能力要求：
- 按实时速率发 PCM（不一次性灌完，模拟真实录音节奏）
- 打印每阶段延迟
- 把返回的 PCM 存成 wav，可用系统播放器直接听
- `--mock` 模式：服务端用 mock 适配器，端到端零 API 调用
- 支持 `--device` 模式：直接连真机同一个地址，验证联通性

**有了它，服务端的正确性、延迟、播放效果全部与硬件解耦。** 设备端写好后只要说同一套协议即可。

## 5. 分阶段任务与验收

### 阶段 0 · 协议与骨架（不依赖任何 API）

| # | 任务 | 验收标准 |
| - | ---- | ---- |
| 0.1 | 建 `geeko_server` 工程 + venv + 依赖 | `uvicorn app.main:app` 能起 |
| 0.2 | 实现协议模型（pydantic）+ 单测 | 畸形 JSON 被拒绝并返回 `bad_proto` |
| 0.3 | WebSocket 接入 + 会话状态机 | 能接连接、收发 ping/pong、断线清理 |
| 0.4 | 三个 mock 适配器 | ASR 返回固定句、翻译加前缀、TTS 生成 1kHz 正弦 |
| 0.5 | 桌面模拟客户端 | 发 wav → 收文本 + PCM，存成 wav 能播放 |
| 0.6 | 计时埋点 | 日志含 `upload_ms / asr_ms / mt_ms / tts_first_ms / total_ms` |

> **阶段 0 结束就可以给设备端开发提供冻结的协议文档** —— 这是解耦并行的关键。

### 阶段 1 · 接真实 ASR

| # | 任务 | 验收标准 |
| - | ---- | ---- |
| 1.1 | 重采样 24k→16k + WAV 封装 | 频谱无明显失真，处理 3s 音频 < 20ms |
| 1.2 | 接 ASR（阿里云/腾讯云/Whisper 择一） | 中文普通话短句准确率 > 90% |
| 1.3 | 语言自动检测 | 中英文都能正确识别并标 `lang` |
| 1.4 | 静音/过短检测 | 空白音频返回 `asr_empty` 而不是报错 |

### 阶段 2 · 接 DeepSeek 翻译

| # | 任务 | 验收标准 |
| - | ---- | ---- |
| 2.1 | 翻译 prompt 设计（去解释、去回显、保标点） | 输出纯净译文，无"译为："之类前缀 |
| 2.2 | 中→英、英→中双向 | 各 20 句抽测，语义准确、无机器味 |
| 2.3 | 输出校验与降级 | 模型抽风时丢弃异常输出，回退到原文 |
| 2.4 | 术语/口语处理 | 日常对话自然，不逐字硬翻 |

> prompt 要点：明确「只输出译文，不要任何解释」；用 `temperature≈0.3`；
> 失败重试一次，仍失败走降级（显示原文）。

### 阶段 3 · 接 TTS + 流式下发

| # | 任务 | 验收标准 |
| - | ---- | ---- |
| 3.1 | 接 TTS，输出 **PCM 24k 单声道 16bit** | 存 wav 播放正常，无杂音 |
| 3.2 | 流式：边收边转发给设备 | 首字节延迟 < 1s |
| 3.3 | 音色可选（配置项 + 协议 `voice` 字段） | 切换音色生效 |
| 3.4 | 长文本分句合成 | 100 字文本不中断、不丢字 |

### 阶段 4 · 延迟优化

| # | 任务 | 验收标准 |
| - | ---- | ---- |
| 4.1 | 阶段并行：收到 ASR 立即发起翻译，收到翻译立即发起 TTS | 总时长 < 各段之和 |
| 4.2 | 分句流水：第一句译完就开始合成，不等全文 | 长句首字节提前 0.5s+ |
| 4.3 | 连接复用（httpx keep-alive / 长连接池） | 省掉每次 TLS 握手 |
| 4.4 | 端到端压测 | 3 秒语音总延迟 ≤ 3.5s（P50） |

### 阶段 5 · 健壮性

| # | 任务 | 验收标准 |
| - | ---- | ---- |
| 5.1 | 各阶段超时与重试 | 上游挂掉时 5s 内返回错误，不卡死 |
| 5.2 | 弱网模拟 | 上传丢帧/延迟抖动仍能完整识别 |
| 5.3 | 并发多设备 | 3 台设备同时说话互不串音（靠 `id` 隔离） |
| 5.4 | 内存与句柄 | 连续 100 次交互无泄漏 |

### 阶段 6 · 设备联调与部署

| # | 任务 | 验收标准 |
| - | ---- | ---- |
| 6.1 | 冻结协议文档（给 C 端） | 字段、时序、错误码齐全，含示例帧 |
| 6.2 | 真机联调 | 按键说话 → LCD 显示 → 喇叭出声 |
| 6.3 | `wss://` + 鉴权 token | 公网可用 |
| 6.4 | 部署脚本 + 日志轮转 | 重启自恢复 |

### 阶段 7 · 可选增强

- 流式 ASR（边说边出字）
- 对话记忆 / 多轮上下文
- 离线降级（本地 whisper.cpp + 本地小模型）
- 翻译质量反馈回路（收集 badcase）

## 6. 风险与预案

| # | 风险 | 影响 | 预案 |
| - | ---- | ---- | ---- |
| 1 | **总延迟偏高**（4~6s） | 体验差 | 识别结果先显示；阶段并行；流式 TTS；分句流水 |
| 2 | **ASR 准确率**（单麦远场 + 噪声） | 识别错 → 翻译错 | 设备端加 AEC/降噪；提示用户靠近说话；增益标定 |
| 3 | **24k→16k 重采样**引入失真或耗时 | 识别率下降 | 用 soxr 高质量模式；处理前做峰值归一化 |
| 4 | **模型输出不纯净**（回显/加解释） | 译文污染 | 强 prompt + 后处理正则 + 长度/语言校验 |
| 5 | **设备 WiFi 弱**导致上传中断 | 交互失败 | 20ms 小帧 + 服务端容忍丢帧；加重连与 `abort` |
| 6 | **成本**随使用增长 | 长期开销 | 见 §7；加缓存（相同文本不重复 TTS） |
| 7 | **ES8388 录音底噪大** | 识别率低 | 服务端做高通滤波（80Hz）+ 音量归一化 |
| 8 | 多设备并发串音 | 数据错乱 | 每连接独立 session，`id` 校验，串行化处理 |

## 7. 成本量级（供参考，随供应商变动）

| 项目 | 量级 | 备注 |
| ---- | ---- | ---- |
| ASR | 每**小时**音频约几元 | 一句 3 秒 ≈ ¥0.003~0.01 |
| 翻译（DeepSeek） | 每句 < ¥0.001 | 输入输出都只有几十 token |
| TTS | 每**万字**约几元 | 一句 20 字 ≈ ¥0.005 |
| **单次交互合计** | **约 ¥0.01** | 1000 次约 ¥10 |

云厂商一般有免费额度，开发阶段基本零成本。真正上量后可以考虑本地模型降本。

## 8. 建议推进顺序

```
阶段0 协议+骨架+mock+模拟客户端   ← 现在就能做，不依赖硬件和 API Key
   ↓  ← 产出：冻结协议文档（设备端可并行开发）
阶段1 ASR  →  阶段2 翻译  →  阶段3 TTS流式
   ↓  ← 每接通一家，用模拟客户端验证一次
阶段4 延迟优化  →  阶段5 健壮性
   ↓
阶段6 真机联调 + 部署  →  阶段7 增强
```

**关键判断：阶段 0 的价值被低估了。** 它不依赖任何 API Key、不依赖硬件，却能：
1. 冻结协议，让设备端 C 代码可以**现在就开始写**
2. 用模拟客户端把"播放是否顺畅""文本是否及时上屏"这些体验问题提前暴露

## 9. 需要你确认的 5 件事

| # | 决策 | 我的建议 | 说明 |
| - | ---- | ---- | ---- |
| 1 | **翻译方向** | 自动检测，中↔英双向 | 固定单向省一点 token，但体验差；自动检测由模型判断 `lang` |
| 2 | **ASR 供应商** | 阿里云或腾讯云 | 中文准确率高、国内延迟低；Whisper 需外网且中文略逊 |
| 3 | **TTS 供应商 + 音色** | 阿里云/腾讯云，先固定一个女声 | 后续通过 `voice` 字段切换 |
| 4 | **部署位置** | 开发用本机局域网，上线再上云 | 避免过早引入 TLS 和公网问题 |
| 5 | **服务端放哪个仓库** | 新建 `geeko_server`（独立仓库或同仓子目录） | 与 ESP32 工程语言不同，独立更清晰 |

另外确认一下：**你手上是否有阿里云/腾讯云/DeepSeek 的 API Key？**
这决定阶段 1~3 能否立即开工，还是先在 mock 上多走一段。
